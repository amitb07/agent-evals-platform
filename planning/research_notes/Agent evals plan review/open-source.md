# Open-source agent-evaluation plan review

Research status: current as of 2026-10-18. “Current” statements below were checked against official documentation, repositories, or specifications on that date. The reviewed file was `agent-evals-solution-plan.md`; it was not modified.

## Are the plan's descriptions and limitations of prior art accurate today?

### Takeaway
Only partly. The plan correctly identifies a gap between an evaluation runner and a Hermes-specific product, but it understates current agent support in Inspect AI, Harbor, promptfoo, Langfuse, Phoenix, DeepEval, and MLflow. “Hermes-aware comparison with a statistical decision” is still a plausible custom layer; sandbox execution, outcome verification, trajectory capture, experiment comparison, and generic eval UI are no longer credible differentiators by themselves.

### Cited Findings
- Inspect AI is not merely a Python prompt-eval library. Its current official overview lists built-in and custom agents, multi-agent primitives, external agents such as Claude Code/Codex CLI/Gemini CLI, more than 200 evaluations, a web viewer, and sandbox backends including Docker, Kubernetes, Modal, Daytona, EC2, Proxmox, Vagrant, and OpenShell. Status: official docs accessed 2026-10-18; repository is MIT-licensed. — [Inspect overview](https://inspect.aisi.org.uk/); [agent support](https://inspect.aisi.org.uk/agents.html); [sandboxing](https://inspect.aisi.org.uk/sandboxing.html); [license](https://raw.githubusercontent.com/UKGovernmentBEIS/inspect_ai/main/LICENSE)
- Inspect provisions per-sample files and isolated environments, supports task/sample-level sandbox definitions, distinguishes expected tool errors from infrastructure failures, and can reproduce a run from an exported YAML/JSON run configuration. Its `.eval` logs can be dumped or converted to JSON and have a published JSON schema. Status: official docs accessed 2026-10-18. — [Sandboxing](https://inspect.aisi.org.uk/sandboxing.html); [log files](https://inspect.aisi.org.uk/eval-logs.html)
- Therefore the plan’s “Inspect is Python-first; the required stack is NestJS/Vue” is factually true about implementation language but not a functional limitation. Inspect can be called as a subprocess/service and its JSON logs ingested by TypeScript; rejecting it solely because the presentation stack is TypeScript conflates UI/API requirements with runner implementation. — [Inspect log commands](https://inspect.aisi.org.uk/reference/inspect_log.html)
- Harbor now describes itself as “any agent with any model on any task in any sandbox in parallel,” supports arbitrary/custom installed agents, local Docker and multiple cloud sandbox providers, retries/concurrency, and an official local web results viewer showing trajectory, reward, cost, and timing. Status: official repository/docs accessed 2026-10-18; repository reports Apache-2.0. — [Harbor repository](https://github.com/harbor-framework/harbor); [run a job](https://docs.harborframework.com/jobs/run-a-job); [custom agents](https://raw.githubusercontent.com/alibaba/harbor/refs/heads/main/docs/content/docs/agents/index.mdx); [results viewer](https://docs.harborframework.com/results/view-job-results)
- Harbor’s task format already packages instructions, a Docker environment, tests, and numeric reward output. It also supports a separate verifier container so grading code and dependencies need not be exposed to or contaminated by the agent container. Status: official docs accessed 2026-10-18. — [Harbor task structure](https://www.harborframework.com/docs/tasks)
- Harbor uses the Agent Trajectory Interchange Format (ATIF), currently documented as ATIF-v1.7, for complete JSON trajectories containing messages, reasoning, tool calls, observations, metrics, subagent trajectories, and extension fields. It provides Pydantic models and a validator. Status: official docs accessed 2026-10-18. — [ATIF documentation](https://docs.harborframework.com/agents/atif); [ATIF RFC](https://github.com/harbor-framework/harbor/blob/main/rfcs/0001-trajectory-format.md)
- Consequently, the plan’s Harbor description is directionally right about its benchmark/CLI orientation and lack of a bespoke A/B statistical verdict, but “no comparison UI” and the implication that trajectory/outcome infrastructure must be custom-built are outdated. Harbor has a results UI and standardized trajectory/reward artifacts, though the reviewed sources did not establish a built-in paired bootstrap decision UI. — [Harbor viewer](https://docs.harborframework.com/results/view-job-results); [ATIF](https://docs.harborframework.com/agents/atif)
- Promptfoo is no longer well characterized as “prompt → response; multi-turn agents possible but not first-class.” Official docs now include coding-agent providers (Codex SDK/app server, Claude Agent SDK, OpenCode, Open Interpreter), OpenTelemetry ingestion, tool/command trajectory normalization, trajectory assertions for tool usage/arguments/sequence/goal success, trace exploration, and trace APIs. Status: official docs accessed 2026-10-18; core remains MIT-licensed after joining OpenAI. — [coding-agent guide](https://www.promptfoo.dev/docs/guides/evaluate-coding-agents/); [providers](https://www.promptfoo.dev/docs/providers/); [tracing](https://www.promptfoo.dev/docs/tracing/); [repository](https://github.com/promptfoo/promptfoo); [license](https://github.com/promptfoo/promptfoo/blob/main/LICENSE)
- Promptfoo exports complete eval data in JSON/JSONL/CSV/HTML/JUnit forms; traced rows carry trace/evaluation IDs, and traces can be exported as JSON for Jaeger, Grafana Tempo, or custom processing. Its own docs warn that exports can contain user data and that sanitizer rules are best-effort. Status: official docs accessed 2026-10-18. — [output formats](https://www.promptfoo.dev/docs/configuration/outputs/); [tracing/export](https://www.promptfoo.dev/docs/tracing/); [CLI export](https://www.promptfoo.dev/docs/usage/command-line/)
- Promptfoo still does not by itself prove safe per-trial filesystem isolation for an arbitrary Hermes process. Its OpenAI Agents documentation explicitly says local hooks/definitions are trusted and mock mode does not isolate them. Thus “no per-trial isolation” can remain a fair limitation only if narrowly stated as “Promptfoo is not the sandbox lifecycle manager for Hermes.” — [OpenAI Agents provider](https://www.promptfoo.dev/docs/providers/openai-agents/)
- Langfuse is more than observability. It has local or hosted datasets, Python and JS/TS experiment runners, concurrency limits, item- and run-level evaluators, per-item traces, error isolation, CI usage, and UI comparison of dataset runs. It also accepts experiments directly through OpenTelemetry attributes. Status: official docs accessed 2026-10-18. — [datasets](https://langfuse.com/docs/evaluation/experiments/datasets); [experiment runner](https://langfuse.com/docs/evaluation/experiments/experiments-via-sdk); [experiment data model](https://langfuse.com/docs/evaluation/experiments/data-model); [OTel experiments](https://langfuse.com/integrations/native/opentelemetry/experiments)
- Langfuse’s core tracing, evaluations, experiments, prompt management, annotation, APIs, and exports are MIT-licensed without usage limits; clearly separated enterprise modules use another license. Self-hosting and an OpenAPI specification are supported. Status: official docs/repository accessed 2026-10-18. — [license](https://github.com/langfuse/langfuse/blob/HEAD/LICENSE); [open-source policy](https://langfuse.com/handbook/chapters/open-source); [public API](https://langfuse.com/docs/api-and-data-platform/features/public-api)
- The plan’s statement that Langfuse is not a sandboxed agent executor remains accurate. Its omission is that Langfuse can replace much of the custom trace store, experiment comparison UI, dataset/versioning, scorer attachment, API, and export work while a separate runner owns containers. — [Langfuse overview of experiment runner](https://langfuse.com/docs/evaluation/experiments/experiments-via-sdk); [OTel ingestion](https://langfuse.com/integrations/native/opentelemetry)
- Phoenix provides OTel/OpenInference tracing, code/LLM/human evaluation, datasets, experiments, prompt versioning, replay, and side-by-side comparison. The server is ELv2 rather than OSI-approved open source; self-hosting is allowed, but providing it as a hosted/managed service is prohibited. Some client/OTel packages are Apache-2.0. Status: official docs/repository accessed 2026-10-18. — [Phoenix overview](https://arize.com/docs/phoenix); [experiments](https://arize.com/docs/phoenix/get-started/get-started-datasets-and-experiments); [server license](https://github.com/Arize-ai/phoenix/blob/main/LICENSE); [license explanation](https://arize.com/docs/phoenix/self-hosting/license)
- DeepEval supports end-to-end outputs, complete agent trajectories, individual tool/retrieval/subagent spans, datasets, concurrent evaluation, and a pytest-like local workflow. It is Apache-2.0. The cited material does not show DeepEval provisioning an isolated execution environment, so it is better viewed as a scorer/test framework than a Hermes sandbox manager. Status: official docs/repository accessed 2026-10-18. — [quickstart](https://deepeval.com/docs/getting-started); [tracing](https://deepeval.com/docs/evaluation-llm-tracing); [repository](https://github.com/confident-ai/deepeval); [license](https://github.com/confident-ai/deepeval/blob/main/LICENSE.md)
- MLflow’s current agent-evaluation path supports datasets, complete traces, custom scorers, built-in tool-call correctness/efficiency judges, evaluating previously captured traces without rerunning the agent, an OTLP endpoint, and OTel export. It is Apache-2.0. It is a broad AI/ML platform, not a purpose-built sandbox harness. Status: official docs/repository accessed 2026-10-18. — [agent evaluation](https://mlflow.org/docs/latest/genai/eval-monitor/running-evaluation/agents/); [trace evaluation](https://mlflow.org/docs/latest/genai/eval-monitor/running-evaluation/traces/); [OTel integration](https://mlflow.org/docs/latest/genai/tracing/opentelemetry/); [license](https://github.com/mlflow/mlflow/blob/master/LICENSE.txt)
- OpenAI Evals remains an MIT-licensed framework/benchmark registry, with separate licenses for some bundled datasets. The hosted OpenAI Evals API is scheduled to become read-only on 2026-10-31 and shut down on 2026-11-30, so it is a poor new platform dependency as of the research date. Status: official docs dated/current on 2026-10-18. — [repository](https://github.com/openai/evals/); [license and dataset exceptions](https://github.com/openai/evals/blob/main/LICENSE.md); [deprecation notice](https://developers.openai.com/api/docs/guides/evals)
- AgentBench is an Apache-2.0 research benchmark across eight interactive environments; its reusable lesson is diverse environment adapters and task-specific success metrics, not a production experiment product. Status: official repository/paper accessed 2026-10-18; benchmark originated in 2023 and was published at ICLR 2024. — [AgentBench repository](https://github.com/THUDM/AgentBench/); [introduction](https://github.com/THUDM/AgentBench/blob/main/docs/Introduction_en.md); [paper](https://arxiv.org/html/2308.03688v3)
- SWE-bench’s current harness creates reproducible Docker environments, applies candidate patches, runs repository tests, separates resolved/unresolved/error states, persists logs/results, supports concurrency, and can re-grade saved logs without rerunning containers. Status: official repository/docs accessed 2026-10-18. — [README](https://github.com/SWE-bench/SWE-bench/blob/main/README.md); [FAQ](https://github.com/SWE-bench/SWE-bench/blob/main/docs/faq.md); [harness](https://github.com/SWE-bench/SWE-bench/tree/main/swebench/harness)
- The METR Task Standard likewise defines a task as environment + instruction + optional state/submission scorer, including network policy and multi-machine resources. This directly precedes the plan’s claimed custom “task + fixture + outcome grader” model. Status: repository text accessed 2026-10-18; its README says the standard was already used for roughly 200 task families and 2,000 tasks as of January 2024. — [METR Task Standard repository](https://github.com/AndonLabs/agent-evals/tree/main)

### Inferences
- The “what we add” paragraph should be narrowed to: a Hermes adapter/profile compiler, controlled A/B semantics, a paired uncertainty decision, and a focused reviewer-friendly UX. Outcome grading and isolation are established prior-art patterns, not additions unique to this proposal.
- A strong critique should distinguish “framework cannot do this” from “framework can do this but would make the required NestJS/Vue product less visible.” The latter is a take-home presentation trade-off, not a capability gap.
- A custom dashboard is defensible if reviewers are assessing product judgment and TypeScript/Vue skill. A custom execution engine, trace format, and generic experiment database are much harder to justify within 6–7 days.

### Gaps
- Official public sources did not establish that Harbor has a built-in paired A/B significance test or confidence-interval verdict; this should be treated as a custom gap unless confirmed in a pinned Harbor release.
- Hermes’ precise headless API, event completeness, profile mutability, self-learning controls, and token accounting were not independently validated in this research. The plan correctly makes these Day-1 spike gates.

## What should be reused versus custom-built for a 6–7 day assignment?

### Takeaway
Build a thin Hermes-specific control plane and comparison experience; reuse an execution/task/trajectory convention. The highest-probability plan is NestJS/Vue/Postgres for the visible product, with Harbor invoked as the trial runner and ATIF ingested as the canonical transcript. If Harbor/Hermes integration fails in the Day-1 spike, retain the same interfaces and fall back to a small Docker adapter rather than rebuilding every framework feature.

### Cited Findings
- Harbor already supplies the concepts closest to the proposed domain: job → trials, task directories, Docker environments, installed custom agents, concurrency/retries, verifier rewards, cloud/local backends, downloadable artifacts, a viewer, and ATIF trajectories. — [run a job](https://docs.harborframework.com/jobs/run-a-job); [task format](https://www.harborframework.com/docs/tasks); [custom agents](https://raw.githubusercontent.com/alibaba/harbor/refs/heads/main/docs/content/docs/agents/index.mdx); [ATIF](https://docs.harborframework.com/agents/atif)
- Inspect is the strongest fallback when richer evaluation semantics, resumability/checkpointing, scorer composition, or multiple sandbox backends matter more than a TypeScript-native runner. Its CLI explicitly supports JSON log export for non-Python orchestration and a round-trip run-config export. — [agents](https://inspect.aisi.org.uk/agents.html); [logs](https://inspect.aisi.org.uk/eval-logs.html)
- Promptfoo is the lowest-friction reuse option for TypeScript-authored assertions, provider adapters, CI output, and OTel trajectory assertions, but it should sit above or beside a sandbox lifecycle manager rather than be represented as the isolation layer. — [providers](https://www.promptfoo.dev/docs/providers/); [tracing](https://www.promptfoo.dev/docs/tracing/); [outputs](https://www.promptfoo.dev/docs/configuration/outputs/)
- Langfuse and Phoenix already provide polished trace/experiment UIs, but adopting either wholesale would reduce the amount of differentiated Vue product work and introduce another operational subsystem. Their strongest use here is as an optional OTLP export target, not a required dependency for the take-home. — [Langfuse OTel](https://langfuse.com/integrations/native/opentelemetry); [Phoenix overview](https://arize.com/docs/phoenix)
- SWE-bench and Harbor both demonstrate that the verifier should consume final environment state after the agent runs; Harbor additionally supports a verifier in a separate clean container. — [SWE-bench FAQ](https://github.com/SWE-bench/SWE-bench/blob/main/docs/faq.md); [Harbor task structure](https://www.harborframework.com/docs/tasks)

### Inferences
- Priority 1 — custom: Hermes adapter/profile snapshot, experiment creation, baseline/candidate invariants, config/task/image digests, run status/failure taxonomy, and the three-screen Vue flow.
- Priority 2 — custom: comparison statistics and explanation. Show paired task deltas, raw repeats, uncertainty, infra exclusions, cost/latency, and links to concrete trace/file/grader evidence.
- Priority 3 — reuse: Harbor task/container/verifier lifecycle and ATIF. Wrap `harbor run` behind a NestJS `Runner` port, ingest its artifacts into Postgres/object storage, and preserve the ability to swap in a direct Docker runner.
- Reuse selectively: a small statistics library for bootstrap intervals; a unified model/provider library only if Hermes does not already account for tokens/cost; Monaco/diff libraries for file display; OTel SDK/exporter for trace portability.
- Do not build in six days: a generic sandbox platform, custom trace protocol, prompt management, annotation queues, evaluator marketplace, multi-user auth, cloud execution, benchmark registry, or full import/export UI.
- Reduce the planned “real experiment” until the system is proven. Twenty tasks × two configs × five repeats is 200 full agent runs plus judge calls and may consume most of the final day. A staged 4-task smoke run, 10-task demonstration run, then optional 20×5 run is more robust.
- The visible product should still be custom enough to satisfy a NestJS/Vue/Postgres assignment: NestJS owns orchestration and normalized persistence; Vue owns comparison/explanation; Harbor is an implementation detail behind a port.

### Gaps
- The exact assignment was not recovered, so it is unknown whether reviewers require all execution/orchestration code to be authored from scratch or merely require the submitted product to use NestJS/Vue/Postgres.
- A pinned compatibility check between the selected Harbor release and Hermes is still required. Search results showed later ecosystem integrations, but no official Harbor Hermes adapter was established from Harbor’s own documentation during this research.

## Are licensing, APIs, sandboxing, trace schemas, or export/import needs missing?

### Takeaway
Yes. The plan needs an explicit dependency/license ledger, an adapter boundary around external APIs, a real sandbox threat model, a portable trace/artifact schema, and reproducible import/export. The most important technical omission is that “fresh Docker container” gives state isolation but is not by itself a security boundary.

### Cited Findings
- License summary as checked 2026-10-18: Inspect MIT; Harbor Apache-2.0; promptfoo MIT; Langfuse core MIT with separate enterprise directories; DeepEval Apache-2.0; MLflow Apache-2.0; AgentBench Apache-2.0; OpenAI Evals MIT with dataset-specific exceptions; Phoenix server ELv2 with Apache-2.0 client/OTel packages. — [Inspect](https://raw.githubusercontent.com/UKGovernmentBEIS/inspect_ai/main/LICENSE); [Harbor](https://github.com/harbor-framework/harbor); [promptfoo](https://github.com/promptfoo/promptfoo/blob/main/LICENSE); [Langfuse](https://github.com/langfuse/langfuse/blob/HEAD/LICENSE); [DeepEval](https://github.com/confident-ai/deepeval/blob/main/LICENSE.md); [MLflow](https://github.com/mlflow/mlflow/blob/master/LICENSE.txt); [AgentBench](https://github.com/THUDM/AgentBench/blob/main/LICENSE); [OpenAI Evals](https://github.com/openai/evals/blob/main/LICENSE.md); [Phoenix](https://github.com/Arize-ai/phoenix/blob/main/LICENSE)
- Langfuse accepts OTLP at `/api/public/otel`, provides JS/TS and Python SDKs, and exposes OpenAPI for self-hosted instances. However, its experiment data model says there is no public REST endpoint for creating experiment runs; users should use the SDK runners or direct OTel ingestion. — [OTel](https://langfuse.com/integrations/native/opentelemetry); [experiment data model](https://langfuse.com/docs/evaluation/experiments/data-model); [public API](https://langfuse.com/docs/api-and-data-platform/features/public-api)
- OpenTelemetry’s official GenAI agent conventions are still marked Development as of 2026-10-18. They cover create/invoke agent, workflow, planning, tool execution, command execution, and skills, but should not be frozen into an irreversible database schema. — [OTel GenAI agent spans](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-agent-spans.md); [GenAI conventions index](https://github.com/open-telemetry/semantic-conventions-genai/tree/main/docs/gen-ai)
- OpenInference is an Apache-2.0 semantic layer on OTel with required span kinds including AGENT, LLM, TOOL, RETRIEVER, GUARDRAIL, and EVALUATOR; it is transport/file-format agnostic and supported by multiple instrumentations. — [OpenInference spec](https://github.com/Arize-ai/openinference/blob/main/spec/semantic_conventions.md); [repository](https://github.com/Arize-ai/openinference)
- ATIF is purpose-built for portable agent trajectories and includes ordered steps, tool calls/observations, metrics, subagents, and extension fields; OTel/OpenInference is purpose-built for distributed traces and backend interoperability. — [ATIF](https://docs.harborframework.com/agents/atif); [OpenInference](https://github.com/Arize-ai/openinference)
- Harbor’s separate verifier environment exists specifically because a shared verifier can see changes/tools/dependencies from the agent environment. — [Harbor task structure](https://www.harborframework.com/docs/tasks)
- Promptfoo warns that complete exports can retain prompts, outputs, variables, traces, media, and non-secret environment values despite best-effort redaction. — [Promptfoo outputs](https://www.promptfoo.dev/docs/configuration/outputs/); [CLI export](https://www.promptfoo.dev/docs/usage/command-line/)

### Inferences
- Add a dependency ledger to the design doc: component, pinned version/commit, license, why used, whether modified/distributed, and dataset/task license/provenance. Phoenix’s ELv2 is acceptable for an internal/self-hosted demo but materially different from MIT/Apache and should not be called OSI open source without qualification.
- Define a `Runner` interface around Harbor/direct Docker and a `TraceSink` around local storage/OTLP. Avoid making Langfuse, Phoenix, or any model provider’s API shape the domain model.
- Use ATIF JSON as the portable transcript artifact and OTel + OpenInference attributes for streaming/observability. Store raw source events too, plus a schema version and transformation version, because both upstream formats evolve.
- Export a self-contained experiment bundle: manifest; task/config snapshots; image digest; fixture hashes; trial statuses; ATIF trajectories; grader definitions/results; score/cost/latency summaries; file diffs or artifact references; software versions; and a redaction report. Support import with schema validation and collision-safe IDs. CSV can remain a convenience summary, not the archival format.
- Pin images by immutable digest, not a mutable tag. Record Hermes commit, runner version, task/config hashes, provider/model identifiers, sampling parameters, retry count, timestamps, and judge prompt/model version.
- Strengthen sandboxing: no privileged containers; no host Docker socket inside the agent; read-only root filesystem where possible; dedicated writable workspace; CPU/memory/PID/time limits; dropped Linux capabilities; seccomp/AppArmor; default-deny network with explicit allowlist; per-trial short-lived credentials; output/artifact quotas; and guaranteed teardown.
- Run graders in a separate clean verifier container or on immutable copied artifacts. If the agent can alter `check_report.py`, PATH, test dependencies, or the grader process, a passing outcome is not trustworthy.
- Define secret and privacy handling: never place provider keys in task fixtures/transcripts, redact tool arguments/outputs, cap transcript payloads, state whether hidden reasoning is collected, and never assume all providers expose chain-of-thought.
- Add cancellation/idempotency/resume semantics: stable trial identity, attempt number, lease/heartbeat, retry reason, and exactly-once result finalization. “Infra failures are retried and never counted” needs a maximum retry policy and an explicit terminal inconclusive state to avoid survivorship bias.
- The statistics design needs revision. Averaging repeats and bootstrapping only 20 tasks estimates variation across tasks but suppresses within-task stochastic variance. Use a hierarchical/cluster bootstrap (resample tasks, then trials within task), or report task-level paired effects with raw repeat distributions. Predeclare handling of missing/infra trials, practical effect threshold, and multiple category comparisons.
- The plan’s “≈10% detectable with 20 tasks” is unsupported without assumed variance and power simulation. Report a simulation under plausible score distributions or remove the number.
- `pass@k` and `pass^k` should state the estimator and independence assumption; repeated provider calls can be correlated by caching, shared outages, or deterministic decoding.

### Gaps
- No primary source was found proving a stable cross-vendor standard for every agent event needed here. OTel GenAI is still Development, so an internal versioned envelope remains necessary.
- Legal conclusions above are engineering observations, not legal advice; transitive dependencies and benchmark datasets need their own license review before redistribution.

## What differentiators will reviewers likely value most?

### Takeaway
Prioritize a working, reproducible Hermes experiment and an evidence-rich comparison UX over breadth. The strongest differentiator is a trustworthy chain from immutable configuration to isolated execution to separate outcome grading to an honest uncertainty decision—not another generic eval dashboard.

### Cited Findings
- Current frameworks already cover generic trace viewing, experiments, and agent scoring, so a generic “runs table + transcript” is crowded prior art. — [Inspect](https://inspect.aisi.org.uk/); [Harbor viewer](https://docs.harborframework.com/results/view-job-results); [Langfuse experiments](https://langfuse.com/docs/evaluation/experiments/experiments-via-sdk); [Phoenix](https://arize.com/docs/phoenix)
- Harbor, SWE-bench, and METR all emphasize executable environments and state-based verification, supporting the plan’s focus on outcomes rather than final text alone. — [Harbor tasks](https://www.harborframework.com/docs/tasks); [SWE-bench FAQ](https://github.com/SWE-bench/SWE-bench/blob/main/docs/faq.md); [METR Task Standard](https://github.com/AndonLabs/agent-evals/tree/main)
- Langfuse, Phoenix, promptfoo, DeepEval, and MLflow already support trace- or trajectory-aware evaluation, so “we capture tool calls” is baseline functionality rather than a differentiator. — [Langfuse OTel](https://langfuse.com/integrations/native/opentelemetry); [Phoenix overview](https://arize.com/docs/phoenix); [promptfoo tracing](https://www.promptfoo.dev/docs/tracing/); [DeepEval tracing](https://deepeval.com/docs/evaluation-llm-tracing); [MLflow agent evaluation](https://mlflow.org/docs/latest/genai/eval-monitor/running-evaluation/agents/)

### Inferences
- Highest value: flawless Day-1 Hermes integration demonstrated end-to-end with captured tool events, immutable config snapshot, final workspace artifacts, token/cost accounting, and clean reset between trials.
- Next: reproducibility and trust. Show image/config/task digests, fixture hashes, separate verifier execution, explicit network/secrets policy, idempotent retries, and agent-vs-infra failure separation.
- Next: an explanation-first compare screen. A reviewer should move from overall effect/uncertainty to task delta to paired run to exact file/test evidence in under a minute.
- Next: statistical honesty. Include raw trial dots, task-level deltas, effect size and CI, practical significance threshold, sample size, exclusions, and “inconclusive” as a legitimate result. Avoid a confident banner produced by fragile assumptions.
- Next: one compelling causal experiment. “Same model, one skill changed” is stronger than comparing unrelated models because the changed variable is interpretable. Include at least one win, one regression, and one flaky task with trace evidence.
- Next: explicit reuse judgment. Reviewers are likely to reward knowing what not to build: explain why Harbor/ATIF or Inspect patterns were adopted and why the Hermes adapter, paired decision, and focused Vue UX remained custom.
- Useful polish: downloadable experiment bundle, one-command setup, seeded deterministic demo mode when API credentials are absent, architecture decision records, tested schemas/stats, and a short video that follows one evidence chain rather than touring every screen.
- Deprioritize: auth, multi-tenancy, live streaming, cloud sandboxes, an evaluator marketplace, and 200 expensive production trials. These add surface area without proving the core evaluation claim.

### Gaps
- Reviewer preferences are inferred from the stated project shape and current prior art; the exact scoring rubric was unavailable because the assignment PDF was not found.
