Agent Evals Platform on Hermes — How it works
An A/B test for agents: change one thing (skill, tool, memory, model) → run the same tasks under config A and config B, k times each → get Better / Worse / Inconclusive with a 95% confidence interval, and see why each run passed or failed. (1= order of steps)
DEFINE · YAML in Git
CONTROL PLANE · docker compose up
EXECUTION · Harbor runs every trial in isolation
DECIDE & EXPLAIN

Task

tasks/*.yaml
  • Prompt + starting files
  • Graders: code checks (some are gates) + LLM judge
  • Reference solution

Agent config

configs/*.yaml
  • Model · skills · toolsets
  • Memory: off or seeded
  • Max turns · pinned Hermes image

Experiment

experiments/*.yaml
  • Baseline A vs candidate B — differ in one thing
  • Task list · k repeats
  • Hypothesis · cost cap (pre-registered)
Trial = 1 task × 1 config × 1 repeat
e.g. E1 skills: 12 tasks × {A,B} × 3 = 72 trials

NestJS Worker

one experiment at a time
  • Compile each config → a fresh Hermes home (skills, memory files, all self-learning off)
  • Generate Harbor task folders + one job file with agents A and B
  • Launch harbor run (k repeats, 4 in parallel)
  • Ingest results → Postgres (API key redacted)
  • Stop if spend hits the cost cap

Harbor (trial runner)

Schedules A and B trials together · CPU/memory limits · network policy · retries provider & sandbox errors only — agent failures count as real failures

① Agent container

new container per trial
  • Pinned Hermes image + fresh Hermes home
  • Network: only api.anthropic.com
  • Runs headless:
    hermes chat -q "<task>" --oneshot
  • Agent uses tools to change files in /app
  • Saves: tool-call events, full session, tokens & cost

② Verifier container

separate, clean — agent never sees graders
  • Receives only the final /app
  • Code checks first — a failed gate caps the score
  • Then LLM judge: blinded to config, stronger model, treats output as untrusted
  • Writes score 0..1 + each check's reason

Anthropic Claude API

Agent model claude-sonnet-5 · Judge model claude-opus-5

Stats

  • Per task: mean score of k repeats for A and B
  • Δ = B − A per task (paired)
  • Bootstrap 95% CI over tasks
CI above 0 → Better below 0 → Worse
contains 0 → Inconclusive (+ min. detectable effect)

Compare screen

“Is B better, and how sure are we?”
  • Verdict banner: effect + 95% CI
  • Δ dot per task
  • pass@1 / pass@k / pass^k per arm
  • Cost, latency, excluded / infra-failed runs

Run detail screen

“Why did this run pass or fail?”
  • Transcript: every tool call, args, output
  • File diff of /app
  • Each grader's score + reason
  • Same task, A vs B side by side

Traceable

Each trial stores a run manifest: image digests, Harbor version, hashes of task, fixtures, compiled home, grader & judge prompt.
